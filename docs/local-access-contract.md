# Temporary local administrator boundary

This is a development-only bootstrap, separate from invitation-only production identity. It is not customer onboarding, production authentication, or a license to expose real data in the open notebook.

## Configuration

The API maps session endpoints only when `ASPNETCORE_ENVIRONMENT=Development`, `AGRO_LOCAL_ADMIN_EMAIL` is set, and `AGRO_LOCAL_ADMIN_PASSWORD` contains at least 24 characters. Generate the password locally; never put credentials in source, committed fixtures, chat, or logs. The HTTP host and local database must bind to `127.0.0.1`. Never enable this bootstrap in staging or production; remove it when verified invitation-based identity is ready.

On Windows, run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/start-backoffice-api.ps1` from the repository to generate DPAPI-protected credentials under ignored `.local/`, start Docker Desktop when its engine is not running, start a separate persistent Docker Compose project `agro-operations-local` on loopback port 5433, apply only the missing additive migrations (`001`, `003` to `008`, piped to `psql` as UTF-8 so accented seed names survive), and serve the protected API on `127.0.0.1:5081`. The script refuses incomplete schemas instead of resetting data. Run `tools/show-backoffice-login.ps1` **interactively** as the same Windows user to reveal the temporary login; never capture its output in logs. These scripts do not connect the login-free preview to real records, generate official prescriptions, or import customer files. `C:\shortcuts\run-agro-operations-local.bat` is the single local launcher: it runs `tools/start-local.ps1`, which starts or reuses this API in its own window, starts or reuses the web server, and opens `/backoffice`; the invented-data notebook stays at `/`.

`POST /api/v1/session` accepts a password, applies a bounded login rate limit and issues an HttpOnly, SameSite=Strict, eight-hour cookie. `GET /api/v1/session` returns the authenticated local identity and a CSRF token; `POST /api/v1/session/logout` requires `X-Agro-CSRF` and clears the session. The data-protection keys live under ignored `.local/keys` for local restarts. A login-free development notebook with invented fixtures remains a separate surface.

When `AGRO_LOCAL_DATABASE` is also configured for a loopback-only PostgreSQL host and the additive schema migrations are applied, `/api/v1/clients`, `/fields`, `/plots`, and `/crops` expose authenticated `GET` lists and `POST` creates; clients, fields and plots also expose `GET /{id}` and each master supports `PUT /{id}` with an expected `revision`. Anonymous requests return 401; every write requires the CSRF header. Blank names return 400, missing parents 404 and stale revisions 409. Do not supply a remote/production database or real records to the open notebook.

The same authenticated routes also cover `/commercial-firms`, `/stages`, `/contractors`, `/inputs`, `/plot-crops` and `/work-orders` (with `/cancel` and `/complete`). Work orders are numbered per commercial firm inside the creating transaction; a cancelled order keeps its number. An order belongs to one firm and may take plots from several fields of that firm's client; `GET /work-orders?q=` searches by number, firm, field or plot, and `GET /work-orders/{id}/document` returns the resolved print document with its workbook-style file name. Creating a client also creates its firm with the same name. Duplicate names, plot codes and crop positions return 409 with a body that names the conflict, distinct from a stale revision.

To preload contractors and inputs from the owner's workbook into the private database, run `tools/import-workbook.ps1 -Workbook <path> [-DryRun]` while the local stack is up. It reads the catalog sheet (contractors, inputs), `BASEDATOS` (clients, fields, plots with code and area) and `Registros` (each firm's next order number after its highest workbook order) without loading macros, prints counts only, skips names that already exist and records unverified provenance for every created row. Real values stay in the private database; the repository and its tests use invented values only.

## Checks

The smoke test uses a generated test password and `example.test` email, and asserts anonymous denial, wrong password rejection, CSRF enforcement, logout and post-logout denial. This does not prove that business endpoints or real-data imports are ready.
